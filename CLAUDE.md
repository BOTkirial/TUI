# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Projet

Trois applications terminal en Python + Textual (client HTTP `http-tui`, client SQL `sql-tui`, gestion Docker `docker-tui`) dans un seul paquet `tui-tools` et une seule image Docker. Le code, les commentaires, les docstrings et les messages UI sont **en français** — conserver cette convention.

## Commandes

```bash
docker compose up -d          # build image + conteneur `tui` (network_mode: host)
./http   |  make http         # démarre la stack si besoin puis `docker compose exec tui http-tui`
./sql    |  make sql          # lance le client SQL
./dock   |  make docker       # lance le client Docker
make build                    # reconstruire l'image après modification du code (le code est COPIÉ, pas monté)
make down / make logs         # logs = conteneur tui

# Dev local sans Docker
pip install -e .
cd workspace/http && http-tui   # lit ./requests/
cd workspace/sql  && sql-tui
```

Aucune suite de tests ni linter configurés.

Important : dans Docker, `workspace/` est monté sur `/work` (plus, pour docker-tui, le socket Docker et `$HOME` en lecture seule au même chemin). Le conteneur `tui` est en `network_mode: host` : `localhost` y désigne la machine hôte (bases locales accessibles telles quelles). Toute modification du code Python exige `make build` puis relancer le conteneur.

## Architecture

**Packaging atypique** : quatre paquets dans des dossiers non standard, mappés par `[tool.setuptools.package-dir]` de `pyproject.toml` :
- `common/tui_common` → `tui_common`
- `http-client/httptui` → `httptui`
- `sql-client/sqltui` → `sqltui`
- `docker-client/dockertui` → `dockertui`

Les imports utilisent ces noms de paquets (`from tui_common import BaseApp`). Un nouveau paquet ou fichier non-`.py` (ex. `.tcss`) doit être déclaré dans `pyproject.toml` **et** copié dans le `Dockerfile`. Textual est épinglé `>=8.2,<9` (le code s'appuie sur des détails internes de Textual 8) ; `.dockerignore` exclut du contexte de build `workspace/`, `.git`, les caches et les secrets (`.env`, exports Postman).

**`tui_common`** : `BaseApp` (sous-classe de `textual.App`) dont héritent les trois TUI — copie automatique de la sélection au `mouse_up` et action `copy_selection` (`ctrl+shift+c`) qui, sans sélection de texte, copie ce que renvoie la méthode `copy_text()` du widget focalisé si elle existe (ex. `ResultsTable` : cellule courante, copiée aussi au double-clic via `Click.chain`) — volontairement absente de la copie auto au clic. La copie passe par `App.copy_to_clipboard` (séquence OSC 52 émise par le driver Textual, `clipboard.py`), ce qui fonctionne à travers Docker/SSH ; la sélection souris des widgets statiques est lue par `screen.get_selected_text()` (portée par l'écran en Textual 8, pas par l'App). `BaseApp.get_system_commands` retire aussi la commande « Screenshot » (capture SVG) de la palette `ctrl+p` — filtre par libellé anglais, fragile si Textual le renomme. Les TUI n'affichent pas de `Header` (bandeau). `BaseApp.notify` force `markup=False` (noms de fichiers/tables et erreurs contiennent des `[`) : afficher aussi tout texte dynamique via `rich.text.Text` dans `Label`/`Static`/listes.

**Partagé dans `tui_common`** : `common.tcss` (chargé en tête de `CSS_PATH = [COMMON_CSS, "app.tcss"]` ; classes `.title`, `.section`, `.hint`, `.framed` = cadre des listes/tableaux/éditeurs, `.button-row` = boutons de même largeur, `.button-bar` = largeur naturelle, `#dialog`/`#dialog-buttons` des modales centrées via `ModalScreen`, `#status`) ; `ConfirmPrompt` (suppression, bouton rouge) ; `AutoWidthTable` (DataTable qui vide son cache de rendu après le calcul des largeurs auto — sinon colonnes tronquées à la largeur de l'en-tête après un filtre) et `CopyTable` (copie de cellule) ; `call_ui(node, fn, *args)` = `call_from_thread` ignoré si l'écran a été fermé (un worker thread n'est pas interrompu : sans garde, NoMatches → l'app quitte). Conventions visuelles : action destructrice en dernier et rouge (`error`), création `success`, action principale `primary` ; raccourcis dans le pied de page, pas dans les libellés ; « Enregistrer » (pas « Sauver ») ; ⏳ en cours, ✓ succès, ✗ erreur ; tri ▲/▼. `textfilter.matches` : filtre des listes (tous les mots, insensible à la casse) partagé par les TUI ; les champs filtre sont créés avec `select_on_focus=False` car la frappe sur la liste/l'arbre y est redirigée (sinon la 1re lettre est sélectionnée puis écrasée).

**Configuration par variables d'environnement** : `HTTP_ROOT`, `HTTP_REQUESTS_DIR` (défaut `$HTTP_ROOT/requests`), `FUZZ_DIR` (optionnelle), `SQL_CONNECTIONS_DIR` — fixées dans `docker-compose.yml`. Côté SQL, `connections.json` (et le `known_hosts` de sqltui) est stocké dans `$SQL_CONNECTIONS_DIR` (`/work/sql/connections` dans Docker, donc `workspace/sql/connections/`, ignoré par git) ou à défaut `$XDG_CONFIG_HOME/sqltui/` (défaut `~/.config`) et `DBEAVER_WORKSPACE` permet de surcharger l'emplacement des données DBeaver à importer (montage actif par défaut dans `docker-compose.yml`).

### Client HTTP (`httptui`)
- `httpfile.py` : modèle `HttpRequest` + lecture/écriture des requêtes. Modèle actuel : **un répertoire `requests/`, un fichier `.http` par requête, sous-dossiers autorisés** (`load_requests_dir` récursif hors dossiers cachés, `list_request_folders`, `save_request`, `serialize_request`) ; le nom de fichier = nom affiché, `HttpRequest.folder` = sous-dossier relatif, pas de ligne `###` ; l'URL de la ligne de requête peut contenir des espaces (` HTTP/x` final retiré), les retours à la ligne des en-têtes sont aplatis à l'écriture. L'écran de liste affiche un `Tree` (`#requests`) qui reflète cette arborescence. `F5` (`action_reload`) relit le disque en conservant la requête sous le curseur et les dossiers dépliés (une requête créée mais jamais sauvée disparaît) ; les autres mises à jour de l'arbre (création d'environnement, import Postman) passent par `_show`, qui reconstruit depuis la mémoire et garde ces requêtes.
- **Deux écrans**, calqués sur le client SQL : `RequestListScreen` (plein écran, poussé par `HttpTui.on_mount`, comme `ConnectionScreen`) = filtre + arbre + Nouvelle / Ouvrir / Actualiser / Supprimer (les imports curl/Postman sont des boutons de la modale « Nouvelle » — `PathPrompt(extra_buttons=…)` — et `ctrl+o`/`ctrl+t`, masqués du pied de page : une rangée de 6 boutons ne tient pas en 80 colonnes) ; ouvrir une requête pousse `RequestScreen(req)` (éditeur, envoi, fuzzing), qui revient par Échap via `dismiss(dernière version de la requête)` — le callback `_request_closed` reconstruit l'arbre (libellé/méthode modifiés) et y replace le curseur. État partagé sur l'app : `requests`, `envs`, `last_env`, `root`, `requests_dir`, `fuzzer`/`fuzz_dir`, `client` (httpx partagé). Les résultats de fuzzing appartiennent à `RequestScreen` (perdus au retour ; les workers de l'écran sont annulés et `_run_fuzz` annule ses tâches restantes). Échap avec modifications non sauvées (`_current_request() != self._request`) avertit une fois.
- Filtre `#request-filter` (même comportement que le filtre des tables SQL : ↑↓ depuis le champ, Entrée ouvre, Échap vide, frappe sur l'arbre redirigée sauf espace). Il **reconstruit** l'arbre (`_build_tree`, porte sur `dossier/nom`) ; les nœuds sont retrouvés par identité (`_node_for`), puis par `_leaf_key` dans `_focus_leaf` (instances recréées par une relecture) ; à défaut, curseur sur la 1re feuille (requête ou environnement). `self._expanded` mémorise les dossiers dépliés avant le filtre pour les restaurer. `_focus_leaf` lit `tree.last_line` avant `move_cursor` : Tree calcule ses lignes paresseusement et `node.line` vaut -1 sinon. Ne pas nommer une méthode d'écran `_closed` (attribut booléen interne de `MessagePump`).
- `envfile.py` : environnements = fichiers `.env.<nom>` (dotenv : `NOM=valeur`, `export`, guillemets) rangés avec les requêtes, ignorés par git (`.gitignore` racine), créés en 0600 (`write_env_text`). Une valeur entre guillemets peut être suivie d'un ` # commentaire` ; lecture par `split("\n")` (pas `splitlines`, qui coupe aussi sur `\x85`/`\u2028`). Ils apparaissent dans l'arbre (`EnvFile`, feuilles « ENV » avant les requêtes de leur dossier) ; Entrée ouvre `EnvScreen` (édition brute du fichier, ctrl+s), « Nouvelle » avec `dossier/.env.nom` en crée un, Suppr le supprime. Portée = **dossier de la requête uniquement** (pas les parents ni sous-dossiers, choix explicite). À l'envoi/fuzz, `RequestScreen._with_env` relit les `.env.*` du dossier et, s'il y en a, ouvre `EnvPrompt` (dernier choix par dossier pré-sélectionné, `app.last_env`) ; `substitute` remplace `{{NOM}}` (regex sans `:` ni `$` : n'affecte pas `{{fuzz:…}}` ni `{{$guid}}` Postman) avant l'expansion du fuzzing, variables non définies laissées telles quelles avec avertissement. Feuilles de l'arbre identifiées par `_leaf_key` (type, dossier, nom) ; `_focus_leaf` sert aux deux types de feuilles.
- `postman.py` : import (`ctrl+t` ou bouton de « Nouvelle », chemin relatif à `HTTP_ROOT`) d'une collection v2.0/v2.1 (dossiers → sous-dossiers, auth Bearer/Basic/apikey héritée, corps raw/urlencoded/graphql ; scripts, formdata, fichiers et autres auth ignorés avec avertissement) ou d'un environnement exporté (→ `.env.<nom>` dans le dossier cible). Variables de collection → `.env.<collection>` écrit dans **chaque** dossier importé (portée par dossier). Rien n'est écrasé : noms de requêtes rendus uniques, `.env` existant conservé ; variables au nom invalide pour `{{…}}` (`base url`) écartées avec avertissement. Export (`ctrl+e`, déclaré `priority=True` car `Input` lie ctrl+e à « fin de ligne » et le filtre a souvent le focus ; pas de bouton) : `to_postman` → collection v2.1 de la requête sous le curseur ou du dossier (récursif, dossiers vides compris, le dossier devient la racine), ou de tout le répertoire (palette : « Export Postman (tout) ») ; corps en mode raw, auth = en-têtes tels quels, `.env.*` non exportés ; fichier relatif à `HTTP_ROOT`, écrasement confirmé, `*.postman_collection.json` ignoré par git (contient les en-têtes d'auth).
- `fuzzer.py` : listes `*.txt` d'un répertoire (`FUZZ_DIR`, défaut `$HTTP_ROOT/fuzz` ; `<empty>` = chaîne vide, aucune liste en dur dans le code), lues **seulement si une requête les référence** puis en cache par mtime (une grosse liste ne ralentit pas chaque envoi) ; expansion des balises `{{fuzz:liste}}` en produit cartésien borné à 500 (`count()` = total réel, troncature signalée). Liste vide = signalée comme introuvable (`missing_lists`). `expand()` renvoie toujours au moins une combinaison ; « envoyer » prend la première, « fuzzer » les envoie toutes.
- `client.py` : envoi async via `httpx`, renvoie un `HttpResult` (les erreurs sont capturées dans `result.error`, pas levées). `send_request(request, client=...)` réutilise un client partagé (keep-alive) ; `brotli`/`zstandard` en dépendances : httpx décode les réponses `br`/`zstd`. `make_client()` le crée avec un `_NoCookieJar` : **aucun cookie reçu n'est mémorisé** (sinon renvoyé en douce à toutes les requêtes et au fuzzing), seul l'en-tête `Cookie` saisi part. Redirections suivies, listées dans `HttpResult.redirects` et affichées (↪) ; `error` = `Type: message` (les timeouts httpx ont un message vide).
- `curlimport.py` : commande curl (« Copy as cURL » bash/POSIX) → `HttpRequest`. Tokeniseur maison façon bash (`'…'`, `"…"`, `$'…'` de Chrome, continuations `\`) car `shlex` ne gère pas `$'…'`. Conserve les credentials, retire `Host`/`Content-Length` ; méthode hors `METHODS` → GET avec avertissement (le `Select` refuserait la valeur). Dialogue `CurlPrompt` dans `app.py`, ouvert par le bouton « Import curl » de la modale « Nouvelle » (`PathPrompt` avec `extra_buttons` ; l'import est lancé depuis le callback de `action_new` car un écran poussé depuis une modale en cours de fermeture perd son callback) ou par `ctrl+o`.
- `app.py` (`RequestScreen`) : UI organisée en onglets `#main-tabs` (Requête — avec sous-onglets Headers/Body — / Réponse / Fuzzing) ; la ligne méthode+URL et les boutons restent hors onglets, l'app bascule d'onglet selon l'action (envoi → Réponse, fuzz → Fuzzing). Création d'une requête = dialogue `PathPrompt` demandant le nom de fichier. Les envois réseau sont des workers async `@work(exclusive=True)` dans des groupes distincts (`send` / `fuzz` : un envoi n'annule pas un fuzzing) ; avancement du fuzzing dans le titre de l'onglet ; cellules du tableau en `Text` (valeurs de fuzz `[/]` = markup) ; le fuzzing part en concurrence bornée (`_FUZZ_CONCURRENCY=16`) sur un client partagé, donc les réponses reviennent dans le désordre et `fuzz_rows` est re-trié par `idx` avant le rendu final. Les résultats sont stockés dans `RequestScreen.fuzz_rows` (`FuzzRow`) ; tri/filtre (debounce 250 ms sur le corps) recalculent la vue via `_filtered_sorted_rows`, le mapping ligne → `FuzzRow` doit survivre au tri/filtre.

### Client SQL (`sqltui`)
- `connections.py` : dataclass `Connection`, `ConnectionStore` (JSON, écriture atomique en 0600 : mots de passe en clair). Un nom de connexion est unique (création comme renommage). Pas d'import `.env` (retiré, inutilisé).
- `app.py` : **deux écrans Textual** (`textual.screen.Screen`). `ConnectionScreen` (plein écran, poussé au démarrage par `SqlTui.on_mount`) gère les connexions (formulaire modal `ConnectionForm`, import DBeaver, suppression) ; une connexion réussie appelle `SqlTui.open_query(db, tables)` qui pousse `QueryScreen` (tables + éditeur SQL + résultats). `QueryScreen` revient en arrière via Échap (1er Échap = vider le filtre). Plein écran des résultats : `ctrl+f` ou bouton compact `#fullscreen` sur la ligne de statut → classe `-results-full` sur l'écran (barre des tables et éditeur en `display: none`, focus forcé sur `#results`) ; Échap en sort avant toute autre chose. `ConnectionScreen` : liste en `1fr` et classe `-short` (`VERTICAL_BREAKPOINTS`, moins de 30 lignes) qui compacte la mise en page pour garder boutons et `#status` visibles en 80x24. Listes connexions/tables = `PickList` (OptionList sans retour circulaire ; pas ListView, qui monte un widget par élément et rame sur des milliers de tables). Suppression d'une connexion confirmée (`ConfirmPrompt`, aussi par Suppr). L'état partagé (`store`) vit sur `SqlTui`, les écrans y accèdent via `self.app` ; la connexion `Database` appartient à `QueryScreen` (passée au constructeur, fermée dans `on_unmount`). Les bindings `ctrl+q`/`ctrl+shift+c` sont déclarés une seule fois dans `BaseApp.BINDINGS`.
- `drivers.py` : `Database` abstrait psycopg (Postgres) et PyMySQL (MySQL/MariaDB). **Appels bloquants** → exécutés dans des workers `@work(thread=True)` portés par l'écran, retour sur le thread UI via `call_ui` ; un `RLock` dans `Database` sérialise toutes les méthodes publiques (`close()` attend la requête en cours). `exclusive=True` ne fait que marquer le worker précédent comme annulé, sans arrêter son thread. `execute(sql, max_rows)` ne conserve que `MAX_ROWS` (10 000) lignes (`QueryResult.truncated`) — curseurs côté client : le pilote reçoit quand même tout le résultat en mémoire — et **valide (commit) après chaque requête**, SELECT compris (sinon transaction ouverte : verrous Postgres, instantané figé MySQL, `UPDATE … RETURNING` perdu). `list_tables` renvoie des noms déjà échappés (Postgres `quote_ident`) ; `quote_table` échappe les noms MySQL non simples. Choix de la base (`ctrl+b`, ou liste des bases d'office si le champ base est vide) pour tous les pilotes : `Database.database` = base courante (la `Connection` n'est pas modifiée) ; `use_database` = `select_db` en MySQL, **nouvelle connexion** en Postgres (même tunnel, `_endpoint`). Les `TableRef` Postgres (schéma, table) ne contiennent pas la base (`table_refs_include_database`) : changer de base vide le résultat affiché, et un résultat arrivé après un changement de base est ignoré.
- **Édition des résultats** : `execute` renseigne `QueryResult.sources` (colonne de table d'origine par colonne du résultat, ou `None`) et `QueryResult.keys` (tables dont la clé primaire est entièrement présente → index de ses colonnes). Origine lue dans les métadonnées du protocole, pas en parsant le SQL : `pgresult.ftable/ftablecol` (Postgres), `cur._result.fields[].org_table/org_name` (PyMySQL, attribut privé). `QueryScreen._edits` = `(ligne, colonne) → str | None` ; `ctrl+s` regroupe en un `RowUpdate` par (ligne, table) et `Database.apply_updates` exécute tout en une transaction (rowcount ≠ 1 → rollback). `ctrl+n` (résultat issu d'une seule table avec sa clé primaire) ajoute une ligne vide en fin de tableau (`QueryScreen._new_rows`, cellules « DEFAULT » tant que non saisies : seules les cellules saisies vont dans l'INSERT, NULL explicite compris) ; au `ctrl+s`, `apply_updates(updates, inserts)` fait les `RowInsert` dans la même transaction et relit la ligne (Postgres `RETURNING`, MySQL `SELECT` par clé primaire + `lastrowid`) pour que la clé générée la rende modifiable. `Suppr` sur le tableau : ligne ajoutée non enregistrée → retrait local ; ligne existante → `ConfirmPrompt` puis `Database.delete_row` immédiat (par clé primaire, rowcount ≠ 1 → rollback), mêmes conditions que `ctrl+n`. La ligne d'un résultat est retrouvée par la **clé de ligne** du DataTable (`_row_at`, clé = index dans `_result.rows`), pas par la coordonnée : une ligne retirée laisse son entrée inutilisée, rien n'est réindexé. Clic sur un en-tête = tri ▲/▼ (`_sort`, remis à zéro par une nouvelle requête) : `_sort_results` reconstruit le tableau avec les cellules déjà rendues et les mêmes clés de ligne, sur les valeurs affichées (modifications comprises ; nombres, même saisis, avant le texte ; NULL/DEFAULT toujours en fin). `_writing` bloque suppression/enregistrement concurrents (les index des workers doivent rester valides), ainsi que l'exécution, le changement de base et le retour aux connexions (qui fermerait la connexion). Changer de base sous Postgres (`ctrl+b` puis Entrée) abandonne d'abord le résultat et ses modifications (avertissement unique), `_switching` bloque l'exécution pendant le changement et `_query_done` écarte un résultat dont `QueryResult.database` n'est pas la base courante. Une table présente deux fois dans le résultat (auto-jointure) est en lecture seule. Valider vide une cellule NULL/DEFAULT la laisse inchangée. Postgres sans nom de base : connexion à `postgres`, choix parmi les bases autorisées (`CONNECT`). Les tableaux Postgres sont convertis en littéral `{…}` par `execute` (OID json/jsonb exclus) et les `timedelta` affichés en `HH:MM:SS`. PyMySQL est connecté avec `CLIENT.FOUND_ROWS` pour que rowcount compte les lignes trouvées. Les cellules sont rendues en `rich.text.Text` (sinon DataTable interprète le contenu comme du markup). `SubmitTextArea` (Entrée = valider) sert à la fois d'éditeur SQL et de champ de la modale `CellEditor`.
- `tunnel.py` : tunnel SSH optionnel par connexion (champs `Connection.ssh_*`, actif si `ssh_enabled` et `ssh_host`). Redirection locale maison sur paramiko (`ThreadingTCPServer` sur 127.0.0.1:port libre → canal `direct-tcpip`) ; `Database.connect()` l'ouvre avant le pilote et `close()` le ferme. L'hôte/port de la base sont vus depuis le serveur SSH. Clés d'hôtes : `~/.ssh/known_hosts` + `known_hosts` de sqltui (à côté de `connections.json`) où un hôte inconnu est mémorisé à la 1re connexion ; clé changée = refus. Un refus d'ouverture de canal par le serveur SSH (ex. « Connect failed ») est mémorisé (`last_error`) et ajouté au message d'erreur de connexion. Une clé introuvable est recherchée par son nom dans `~/.ssh` (monté en lecture seule dans Docker).
- `dumpcmd.py` : commandes shell copiées par la palette `ctrl+p` (« Copier la commande de dump / de restauration », `SqlTui._copy_command`) pour la connexion surlignée (`ConnectionScreen`) ou la base courante (`QueryScreen._database`, suit `ctrl+b`). Dump SQL texte `pg_dump --no-owner --no-privileges` / `mysqldump` (`mariadb-dump` si driver mariadb) vers `~/Téléchargements/<base>_<horodatage>.sql` ; restauration `psql`/`mysql` par stdin, terminée par `< ~/Téléchargements/` (nom à compléter). Mot de passe inclus (`PGPASSWORD`, `--password`) → commande préfixée d'une espace (hors historique bash) ; tunnel SSH → `ssh … 'cmd'` exécuté sur le serveur SSH.
- `dbeaver.py` : import des connexions DBeaver (`data-sources.json` + déchiffrement local de `credentials-config.json` via `cryptography` — fichier binaire brut, base64 en repli) ; tunnel repris de `configuration.handlers.ssh_tunnel` (utilisateur/mot de passe SSH dans l'entrée `network/ssh_tunnel` des identifiants, `keyPath` réécrit en `~/.ssh/…`, jump servers ignorés) ; en cas d'échec du déchiffrement, seules les métadonnées sont importées ; sections `null` tolérées ; moteur d'après `provider` (MariaDB : `driver` contenant « maria ») ; noms en double suffixés « (2) »… ; une connexion locale de même nom est conservée (comptée comme ignorée), donc un réimport ne remplace rien.

### Client Docker (`dockertui`)
- `engine.py` : tout passe par le **CLI `docker`** (sous-processus, `--format '{{json .}}'`), pas de SDK — le même binaire sert à `docker compose`. Image : CLI + plugin compose copiés depuis `docker:29-cli` dans le `Dockerfile` ; le démon est celui de l'hôte via `/var/run/docker.sock` monté. `snapshot()` lit tout en une fois (`container inspect` de tous les conteneurs → montages/réseaux/labels, puis images/réseaux/volumes avec leurs conteneurs utilisateurs). Les stacks sont reconstituées depuis les labels `com.docker.compose.*` ; `compose()` passe `-f <config_files> --project-directory <working_dir>` pour `up` (chemins hôte, d'où `$HOME` monté au même chemin, lecture seule) et seulement `-p` pour `stop`/`down` ; `up` est lancé avec `HOME`/`USER` de l'hôte (`HOST_HOME`/`HOST_USER` fixées par docker-compose.yml, `DOCKER_CONFIG` laissé sur `/root/.docker`) pour que `${HOME}`/`${USER}` des fichiers compose se résolvent comme sur l'hôte. Erreurs = `DockerError` (stderr du CLI ; `tail(n)` = dernières lignes non vides : la dernière dans `#status`, borné à 3 lignes dans l'app.tcss Docker, les 6 dernières dans la notification). Toute commande passe par `_popen` : groupe de processus dédié (`start_new_session`, le plugin compose est un fils du CLI), suivi dans `_processes`, tué (`killpg`) au délai dépassé et à la sortie de l'app (`DockerTui.on_unmount` → `engine.kill_all`, sinon ctrl+q attend la fin des workers thread) ; `init: true` dans docker-compose.yml récupère les zombies. `container inspect` en code 1 (conteneur supprimé entre `ps` et `inspect`) : le stdout JSON est accepté.
- `app.py` : un écran `DockerScreen` (poussé par `DockerTui.on_mount`) avec `TabbedContent` (Conteneurs / Images / Réseaux / Volumes). Chaque onglet est un `FilterPane` (filtre + liste ; ↑↓ et Suppr depuis le champ, frappe redirigée — logique dans `on_key` du pane) ; `ResourcePane` = tableau `CopyTable` (copie de cellule au double-clic / `copy_text`) + suppression confirmée, spécialisé par `ImagesPane`/`NetworksPane`/`VolumesPane` (`key`, `cells`, `remove`, `filter_text`, libellés `a_noun`/`the_noun`/`plural`, `rm_command`…). `ContainersPane` = case « En route uniquement » (`#running-only`, cochée par défaut, combinée au filtre texte) + arbre stacks → conteneurs (`_node_key` pour retrouver le curseur après reconstruction, stacks repliées mémorisées hors filtre : `_collapsed` n'est mis à jour que pour les stacks affichées, une stack masquée par le filtre ou « En route uniquement » garde son état, et les replis de secours du curseur ne déplient rien) + panneau détail. Appels docker dans des workers thread (`_load` exclusif, dont le rappel UI ignore le résultat si le worker a été annulé entre-temps — `worker.is_cancelled`, testé sur le thread UI ; `run_docker` non exclusif puis rechargement). Up/Stop/Down/suppression sur la stack ou le conteneur qui exécute la TUI (`engine.own_container_id()`, lu dans `/proc/self/mountinfo` — pas le nom d'hôte, `network_mode: host`) demandent une confirmation (`ConfirmPrompt`) prévenant que la TUI sera arrêtée. `refresh_view(filter_changed)` : filtre modifié → 1er résultat, données rechargées → curseur conservé (élément disparu, ex. supprimé → son voisin à la même ligne) ; `DataTable.clear()` remet le défilement à 0, `ResourcePane` le restaure via `call_after_refresh` (hauteur virtuelle recalculée seulement à l'idle). Suppr agit sur l'onglet *affiché* (`screen.action_delete`) car le focus peut rester un instant dans le filtre de l'onglet précédent ; changement d'onglet via `Tabs.action_next_tab` (affecter `TabbedContent.active` deux fois de suite perd parfois le 2e changement).
- `LogScreen` (bouton « Logs » / `F9` sur un conteneur ou une stack) : `engine.follow_logs` lance `docker logs -f` (ou `docker compose -p … logs -f`) en `Popen` (sortie en octets), lu par blocs `os.read` dans un worker thread (fin de ligne = `\n`, `\r\n` ou `\r` seul, pour les barres de progression ; ligne sans fin coupée à 64 Kio) ; les lignes brutes vont dans un `deque` borné (`_MAX_PENDING`, les plus anciennes sautées et signalées) et un `set_interval` (200 ms) les décode et les écrit en **un seul** `RichLog.write` — un write par ligne ou un tampon non borné fige l'app sur un gros débit. « Suivre » (`ctrl+f`) = `RichLog.auto_scroll`. Le processus (tout son groupe) est arrêté par `engine.stop_logs` dans `on_unmount` (`_closing` couvre la fermeture avant l'affectation de `_proc`).
