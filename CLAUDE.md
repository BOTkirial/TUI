# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Projet

Trois applications terminal en Python + Textual (client HTTP `http-tui`, client SQL `sql-tui`, gestion Docker `docker-tui`) dans un seul paquet `tui-tools` et une seule image Docker. Le code, les commentaires, les docstrings et les messages UI sont **en français** — conserver cette convention.

## Commandes

```bash
docker compose up -d          # build image + conteneur `tui` (network_mode: host)
./http   |  make http         # démarre la stack si besoin puis `docker compose exec tui http-tui`
./sql    |  make sql          # lance le client SQL
./dock   |  make docker       # lance le client Docker
make build                    # reconstruire l'image après modification du code (le code est COPIÉ, pas monté)
make down / make logs         # logs = conteneur tui

# Dev local sans Docker
pip install -e .
cd workspace/http && http-tui   # lit ./requests/
cd workspace/sql  && sql-tui
```

Aucune suite de tests ni linter configurés.

Important : dans Docker, `workspace/` est monté sur `/work` (plus, pour docker-tui, le socket Docker et `$HOME` en lecture seule au même chemin). Le conteneur `tui` est en `network_mode: host` : `localhost` y désigne la machine hôte (bases locales accessibles telles quelles). Toute modification du code Python exige `make build` puis relancer le conteneur.

## Architecture

**Packaging atypique** : quatre paquets dans des dossiers non standard, mappés par `[tool.setuptools.package-dir]` de `pyproject.toml` :
- `common/tui_common` → `tui_common`
- `http-client/httptui` → `httptui`
- `sql-client/sqltui` → `sqltui`
- `docker-client/dockertui` → `dockertui`

Les imports utilisent ces noms de paquets (`from tui_common import BaseApp`). Un nouveau paquet ou fichier non-`.py` (ex. `.tcss`) doit être déclaré dans `pyproject.toml` **et** copié dans le `Dockerfile`.

**`tui_common`** : `BaseApp` (sous-classe de `textual.App`) dont héritent les trois TUI — copie automatique de la sélection au `mouse_up` et action `copy_selection` (`ctrl+shift+c`) qui, sans sélection de texte, copie ce que renvoie la méthode `copy_text()` du widget focalisé si elle existe (ex. `ResultsTable` : cellule courante, copiée aussi au double-clic via `Click.chain`) — volontairement absente de la copie auto au clic. La copie passe par `App.copy_to_clipboard` avec repli OSC 52 manuel (`clipboard.py`), ce qui fonctionne à travers Docker/SSH. `BaseApp.get_system_commands` retire aussi la commande « Screenshot » (capture SVG) de la palette `ctrl+p` — filtre par libellé anglais, fragile si Textual le renomme. Les TUI n'affichent pas de `Header` (bandeau). `BaseApp.notify` force `markup=False` (noms de fichiers/tables et erreurs contiennent des `[`) : afficher aussi tout texte dynamique via `rich.text.Text` dans `Label`/`Static`/listes.

**Partagé dans `tui_common`** : `common.tcss` (chargé en tête de `CSS_PATH = [COMMON_CSS, "app.tcss"]` ; classes `.title`, `.section`, `.hint`, `.framed` = cadre des listes/tableaux/éditeurs, `.button-row` = boutons de même largeur, `.button-bar` = largeur naturelle, `#dialog`/`#dialog-buttons` des modales centrées via `ModalScreen`, `#status`) ; `ConfirmPrompt` (suppression, bouton rouge) ; `AutoWidthTable` (DataTable qui vide son cache de rendu après le calcul des largeurs auto — sinon colonnes tronquées à la largeur de l'en-tête après un filtre) et `CopyTable` (copie de cellule) ; `call_ui(node, fn, *args)` = `call_from_thread` ignoré si l'écran a été fermé (un worker thread n'est pas interrompu : sans garde, NoMatches → l'app quitte). Conventions visuelles : action destructrice en dernier et rouge (`error`), création `success`, action principale `primary` ; raccourcis dans le pied de page, pas dans les libellés ; « Enregistrer » (pas « Sauver ») ; ⏳ en cours, ✓ succès, ✗ erreur ; tri ▲/▼. `textfilter.matches` : filtre des listes (tous les mots, insensible à la casse) partagé par les TUI ; les champs filtre sont créés avec `select_on_focus=False` car la frappe sur la liste/l'arbre y est redirigée (sinon la 1re lettre est sélectionnée puis écrasée). `envfile.py` : parseur `.env` maison et découverte des `.env*` (racine + sous-dossiers directs) — utilisé seulement par le client SQL ; le client HTTP n'a pas de notion d'environnement (`{{VAR}}` n'est pas substitué).

**Configuration par variables d'environnement** : `HTTP_ROOT`, `HTTP_REQUESTS_DIR` (défaut `$HTTP_ROOT/requests`), `FUZZ_DIR` (optionnelle), `SQL_ROOT`, `SQL_CONNECTIONS_DIR` — fixées dans `docker-compose.yml`. Côté SQL, `connections.json` (et le `known_hosts` de sqltui) est stocké dans `$SQL_CONNECTIONS_DIR` (`/work/sql/connections` dans Docker, donc `workspace/sql/connections/`, ignoré par git) ou à défaut `$XDG_CONFIG_HOME/sqltui/` (défaut `~/.config`) et `DBEAVER_WORKSPACE` permet de surcharger l'emplacement des données DBeaver à importer (montage actif par défaut dans `docker-compose.yml`).

### Client HTTP (`httptui`)
- `httpfile.py` : modèle `HttpRequest` + lecture/écriture des requêtes. Modèle actuel : **un répertoire `requests/`, un fichier `.http` par requête, sous-dossiers autorisés** (`load_requests_dir` récursif hors dossiers cachés, `list_request_folders`, `save_request`, `serialize_request`) ; le nom de fichier = nom affiché, `HttpRequest.folder` = sous-dossier relatif, pas de ligne `###`. L'écran de liste affiche un `Tree` (`#requests`) qui reflète cette arborescence. `F5` (`action_reload`) relit le disque en conservant la requête sous le curseur et les dossiers dépliés (une requête créée mais jamais sauvée disparaît).
- **Deux écrans**, calqués sur le client SQL : `RequestListScreen` (plein écran, poussé par `HttpTui.on_mount`, comme `ConnectionScreen`) = filtre + arbre + Nouvelle / Ouvrir / Import curl / Actualiser ; ouvrir une requête pousse `RequestScreen(req)` (éditeur, envoi, fuzzing), qui revient par Échap via `dismiss(dernière version de la requête)` — le callback `_request_closed` reconstruit l'arbre (libellé/méthode modifiés) et y replace le curseur. État partagé sur l'app : `requests`, `requests_dir`, `fuzzer`/`fuzz_dir`, `client` (httpx partagé). Les résultats de fuzzing appartiennent à `RequestScreen` (perdus au retour ; les workers de l'écran sont annulés et `_run_fuzz` annule ses tâches restantes). Échap avec modifications non sauvées (`_current_request() != self._request`) avertit une fois.
- Filtre `#request-filter` (même comportement que le filtre des tables SQL : ↑↓ depuis le champ, Entrée ouvre, Échap vide, frappe sur l'arbre redirigée sauf espace). Il **reconstruit** l'arbre (`_build_tree`, porte sur `dossier/nom`) ; les nœuds sont retrouvés par identité de requête (`_node_for`). `self._expanded` mémorise les dossiers dépliés avant le filtre pour les restaurer. `_focus_request` lit `tree.last_line` avant `move_cursor` : Tree calcule ses lignes paresseusement et `node.line` vaut -1 sinon. Ne pas nommer une méthode d'écran `_closed` (attribut booléen interne de `MessagePump`).
- `fuzzer.py` : listes chargées depuis `*.txt` d'un répertoire (`FUZZ_DIR`, défaut `$HTTP_ROOT/fuzz`, relu avant chaque envoi ; `<empty>` = chaîne vide, aucune liste en dur dans le code), expansion des balises `{{fuzz:liste}}` en produit cartésien borné à 500. `expand()` renvoie toujours au moins une combinaison ; « envoyer » prend la première, « fuzzer » les envoie toutes.
- `client.py` : envoi async via `httpx`, renvoie un `HttpResult` (les erreurs sont capturées dans `result.error`, pas levées). `send_request(request, client=...)` réutilise un client partagé (keep-alive) ; `make_client()` le crée.
- `curlimport.py` : commande curl (« Copy as cURL » bash/POSIX) → `HttpRequest`. Tokeniseur maison façon bash (`'…'`, `"…"`, `$'…'` de Chrome, continuations `\`) car `shlex` ne gère pas `$'…'`. Conserve les credentials, retire `Host`/`Content-Length`. Dialogue `CurlPrompt` dans `app.py`, ouvert par le bouton « Import curl » de la modale « Nouvelle » (`PathPrompt` avec `alt_label` ; l'import est lancé depuis le callback de `action_new` car un écran poussé depuis une modale en cours de fermeture perd son callback) ou par `ctrl+o`.
- `app.py` (`RequestScreen`) : UI organisée en onglets `#main-tabs` (Requête — avec sous-onglets Headers/Body — / Réponse / Fuzzing) ; la ligne méthode+URL et les boutons restent hors onglets, l'app bascule d'onglet selon l'action (envoi → Réponse, fuzz → Fuzzing). Création d'une requête = dialogue `PathPrompt` demandant le nom de fichier. Les envois réseau sont des workers async `@work(exclusive=True)` ; le fuzzing part en concurrence bornée (`_FUZZ_CONCURRENCY=16`) sur un client partagé, donc les réponses reviennent dans le désordre et `fuzz_rows` est re-trié par `idx` avant le rendu final. Les résultats sont stockés dans `RequestScreen.fuzz_rows` (`FuzzRow`) ; tri/filtre (debounce 250 ms sur le corps) recalculent la vue via `_filtered_sorted_rows`, le mapping ligne → `FuzzRow` doit survivre au tri/filtre.

### Client SQL (`sqltui`)
- `connections.py` : dataclass `Connection`, `ConnectionStore` (JSON), construction depuis `.env` (`DATABASE_URL` ou `DB_HOST`/`DB_PORT`/…) avec normalisation du driver (`postgres`, `mysql`, `mariadb`).
- `app.py` : **deux écrans Textual** (`textual.screen.Screen`). `ConnectionScreen` (plein écran, poussé au démarrage par `SqlTui.on_mount`) gère les connexions (formulaire modal `ConnectionForm`, import DBeaver/`.env`, suppression) ; une connexion réussie appelle `SqlTui.open_query(db, tables)` qui pousse `QueryScreen` (tables + éditeur SQL + résultats). `QueryScreen` revient en arrière via Échap (1er Échap = vider le filtre). Listes connexions/tables = `PickList` (OptionList sans retour circulaire ; pas ListView, qui monte un widget par élément et rame sur des milliers de tables). Suppression d'une connexion confirmée (`ConfirmPrompt`, aussi par Suppr). L'état partagé (`store`, `root`) vit sur `SqlTui`, les écrans y accèdent via `self.app` ; la connexion `Database` appartient à `QueryScreen` (passée au constructeur, fermée dans `on_unmount`). Les bindings `ctrl+q`/`ctrl+shift+c` sont déclarés une seule fois dans `BaseApp.BINDINGS`.
- `drivers.py` : `Database` abstrait psycopg (Postgres) et PyMySQL (MySQL/MariaDB). **Appels bloquants** → exécutés dans des workers `@work(thread=True)` portés par l'écran, retour sur le thread UI via `call_ui`. `execute(sql, max_rows)` lit au plus `MAX_ROWS` (10 000) lignes (`QueryResult.truncated`) et **valide (commit) après chaque requête**, SELECT compris (sinon transaction ouverte : verrous Postgres, instantané figé MySQL, `UPDATE … RETURNING` perdu). `list_tables` renvoie des noms déjà échappés (Postgres `quote_ident`) ; `quote_table` échappe les noms MySQL non simples.
- **Édition des résultats** : `execute` renseigne `QueryResult.sources` (colonne de table d'origine par colonne du résultat, ou `None`) et `QueryResult.keys` (tables dont la clé primaire est entièrement présente → index de ses colonnes). Origine lue dans les métadonnées du protocole, pas en parsant le SQL : `pgresult.ftable/ftablecol` (Postgres), `cur._result.fields[].org_table/org_name` (PyMySQL, attribut privé). `QueryScreen._edits` = `(ligne, colonne) → str | None` ; `ctrl+s` regroupe en un `RowUpdate` par (ligne, table) et `Database.apply_updates` exécute tout en une transaction (rowcount ≠ 1 → rollback). PyMySQL est connecté avec `CLIENT.FOUND_ROWS` pour que rowcount compte les lignes trouvées. Les cellules sont rendues en `rich.text.Text` (sinon DataTable interprète le contenu comme du markup). `SubmitTextArea` (Entrée = valider) sert à la fois d'éditeur SQL et de champ de la modale `CellEditor`.
- `tunnel.py` : tunnel SSH optionnel par connexion (champs `Connection.ssh_*`, actif si `ssh_enabled` et `ssh_host`). Redirection locale maison sur paramiko (`ThreadingTCPServer` sur 127.0.0.1:port libre → canal `direct-tcpip`) ; `Database.connect()` l'ouvre avant le pilote et `close()` le ferme. L'hôte/port de la base sont vus depuis le serveur SSH. Clés d'hôtes : `~/.ssh/known_hosts` + `known_hosts` de sqltui (à côté de `connections.json`) où un hôte inconnu est mémorisé à la 1re connexion ; clé changée = refus. Une clé introuvable est recherchée par son nom dans `~/.ssh` (monté en lecture seule dans Docker).
- `dumpcmd.py` : commandes shell copiées par la palette `ctrl+p` (« Copier la commande de dump / de restauration », `SqlTui._copy_command`) pour la connexion surlignée (`ConnectionScreen`) ou la base courante (`QueryScreen._database`, suit `ctrl+b`). Dump SQL texte `pg_dump --no-owner --no-privileges` / `mysqldump` (`mariadb-dump` si driver mariadb) vers `~/Téléchargements/<base>_<horodatage>.sql` ; restauration `psql`/`mysql` par stdin, terminée par `< ~/Téléchargements/` (nom à compléter). Mot de passe inclus (`PGPASSWORD`, `--password`) → commande préfixée d'une espace (hors historique bash) ; tunnel SSH → `ssh … 'cmd'` exécuté sur le serveur SSH.
- `dbeaver.py` : import des connexions DBeaver (`data-sources.json` + déchiffrement local de `credentials-config.json` via `cryptography` — fichier binaire brut, base64 en repli) ; tunnel repris de `configuration.handlers.ssh_tunnel` (utilisateur/mot de passe SSH dans l'entrée `network/ssh_tunnel` des identifiants, `keyPath` réécrit en `~/.ssh/…`, jump servers ignorés) ; en cas d'échec du déchiffrement, seules les métadonnées sont importées.

### Client Docker (`dockertui`)
- `engine.py` : tout passe par le **CLI `docker`** (sous-processus, `--format '{{json .}}'`), pas de SDK — le même binaire sert à `docker compose`. Image : CLI + plugin compose copiés depuis `docker:29-cli` dans le `Dockerfile` ; le démon est celui de l'hôte via `/var/run/docker.sock` monté. `snapshot()` lit tout en une fois (`container inspect` de tous les conteneurs → montages/réseaux/labels, puis images/réseaux/volumes avec leurs conteneurs utilisateurs). Les stacks sont reconstituées depuis les labels `com.docker.compose.*` ; `compose()` passe `-f <config_files> --project-directory <working_dir>` pour `up` (chemins hôte, d'où `$HOME` monté au même chemin, lecture seule) et seulement `-p` pour `stop`/`down`. Erreurs = `DockerError` (stderr du CLI).
- `app.py` : un écran `DockerScreen` (poussé par `DockerTui.on_mount`) avec `TabbedContent` (Conteneurs / Images / Réseaux / Volumes). Chaque onglet est un `FilterPane` (filtre + liste ; ↑↓ et Suppr depuis le champ, frappe redirigée — logique dans `on_key` du pane) ; `ResourcePane` = tableau `CopyTable` (copie de cellule au double-clic / `copy_text`) + suppression confirmée, spécialisé par `ImagesPane`/`NetworksPane`/`VolumesPane` (`key`, `cells`, `remove`, `filter_text`, libellés `a_noun`/`the_noun`/`plural`, `rm_command`…). `ContainersPane` = case « En route uniquement » (`#running-only`, cochée par défaut, combinée au filtre texte) + arbre stacks → conteneurs (`_node_key` pour retrouver le curseur après reconstruction, stacks repliées mémorisées hors filtre) + panneau détail. Appels docker dans des workers thread (`_load` exclusif, `run_docker` non exclusif puis rechargement). `refresh_view(filter_changed)` : filtre modifié → 1er résultat, données rechargées → curseur conservé (élément disparu, ex. supprimé → son voisin à la même ligne) ; `DataTable.clear()` remet le défilement à 0, `ResourcePane` le restaure via `call_after_refresh` (hauteur virtuelle recalculée seulement à l'idle). Suppr agit sur l'onglet *affiché* (`screen.action_delete`) car le focus peut rester un instant dans le filtre de l'onglet précédent ; changement d'onglet via `Tabs.action_next_tab` (affecter `TabbedContent.active` deux fois de suite perd parfois le 2e changement).
- `LogScreen` (bouton « Logs » / `F9` sur un conteneur ou une stack) : `engine.follow_logs` lance `docker logs -f` (ou `docker compose -p … logs -f`) en `Popen` (sortie en octets), lu par blocs `os.read` dans un worker thread ; les lignes brutes vont dans un `deque` borné (`_MAX_PENDING`, les plus anciennes sautées et signalées) et un `set_interval` (200 ms) les décode et les écrit en **un seul** `RichLog.write` — un write par ligne ou un tampon non borné fige l'app sur un gros débit. « Suivre » (`ctrl+f`) = `RichLog.auto_scroll`. Le processus est terminé dans `on_unmount` (`_closing` couvre la fermeture avant l'affectation de `_proc`).
